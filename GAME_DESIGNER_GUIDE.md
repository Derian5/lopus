# Гайд по игровому контенту

Этот документ описывает, как без изменения боевой логики настраивать и добавлять героев, солдатские профессии, врагов, боссов, способности, статусы, предметы, столкновения и контент рынка.

## 1. Где находится контент

| Назначение | Путь |
|---|---|
| Игровые ресурсы | `res://content/demo/` |
| Описания типов ресурсов | `res://content/definitions/` |
| Способности | `res://content/demo/abilities/` |
| Статусы | `res://content/demo/statuses/` |
| Предметы | `res://content/demo/items/` |
| Столкновения | `res://content/demo/encounters/` |
| Враги и боссы | `res://content/demo/` и `res://content/demo/enemies/` |
| Длина маршрута и волна Boss | `res://content/demo/routes/demo_route.tres` |
| Стартовый состав и инвентарь | `res://data/runtime/demo_run_factory.gd` |
| Генерация рынка | `res://data/runtime/market_generator.gd` |
| Покупка, продажа и reroll | `res://data/runtime/market_service.gd` |

`ContentRegistry` при запуске рекурсивно загружает все файлы `.tres` из `res://content/demo/`. Ручная регистрация нового ресурса обычно не нужна.

Ресурс будет зарегистрирован, если:

- он сохранён внутри `res://content/demo/`;
- он наследует `ContentDefinition`;
- поле `id` заполнено;
- его `id` уникален во всём проекте;
- ресурс не содержит `Node` или `NodePath`.

## 2. Рекомендуемый рабочий процесс

Самый безопасный способ создать контент:

1. Найти наиболее похожий существующий `.tres`.
2. В панели FileSystem Godot нажать правой кнопкой и выбрать `Duplicate`.
3. Переместить копию в подходящий каталог внутри `res://content/demo/`.
4. Открыть копию в Inspector.
5. Сразу заменить `id`, `display_name` и `description`.
6. Настроить игровые поля.
7. Запустить игру и тесты из раздела 13.

Дублирование предпочтительнее создания пустого ресурса: оно сохраняет правильные типы вложенных ресурсов и массивов. `.tres` являются текстовыми файлами, поэтому их можно редактировать вручную, но Godot Inspector безопаснее для ссылок на другие ресурсы.

### Общие поля любого контента

| Поле | Назначение |
|---|---|
| `id` | Постоянный технический идентификатор |
| `display_name` | Имя в интерфейсе |
| `description` | Описание и подсказка |
| `icon` | Иконка, если интерфейс её использует |
| `tags` | Метки для логики и классификации |

Рекомендуемые префиксы ID:

| Тип | Формат | Пример |
|---|---|---|
| Герой | `hero.*` | `hero.test_vanguard` |
| Профессия | `job.*` | `job.warrior` |
| Враг или босс | `enemy.*` | `enemy.iron_warden` |
| Столкновение | `encounter.*` | `encounter.warden_guard` |
| Способность | `ability.*` | `ability.fire_bolt` |
| Статус | `status.*` | `status.burn` |
| Предмет героя | `item.hero.*` | `item.hero.titan_seal` |
| Предмет солдата | `item.soldier.*` | В текущем prototype отсутствует |
| Эффект | `effect.*` | `effect.fire_bolt_damage` |

Не меняйте `id` уже выпущенного контента без необходимости. Сохранения хранят ID, поэтому переименование или удаление ID может сделать старое сохранение невалидным. Имя файла и `display_name` менять безопаснее.

## 3. Характеристики юнитов

`StatBlock` содержит:

| Поле | Значение |
|---|---|
| `max_hp` | Максимальное здоровье |
| `damage` | Урон базовой атаки |
| `attack_speed` | Число базовых атак в секунду |
| `movement_speed` | Скорость перемещения |
| `attack_range` | Дистанция базовой атаки |
| `armor` | Броня |

Урон эффектов способности не масштабируется автоматически от `damage`. Например, `DamageEffect.amount = 20` всегда создаёт 20 сырого урона до обработки бронёй независимо от `damage` владельца.

### Герой или враг

У героя и врага `base_stats` являются полными базовыми характеристиками. Если требуется 300 HP и 25 урона, укажите непосредственно `max_hp = 300` и `damage = 25`.

### Солдатская профессия

У профессии `stat_modifiers` являются прибавками к базовому ополченцу, а не итоговыми характеристиками.

База любого солдата до профессии:

| Характеристика | База |
|---|---:|
| HP | 105 |
| Damage | 10 |
| Attack Speed | 1.0 |
| Movement Speed | 108 |
| Attack Range | 46 |
| Armor | 2 |

Например, профессия с `max_hp = 80`, `damage = 2`, `armor = 12` получит 185 HP, 12 damage и 14 armor до veterancy и предметов.

Критически важно: новый `StatBlock` имеет ненулевые значения по умолчанию. Не создавайте для профессии пустой `StatBlock`, иначе она случайно получит +100 HP, +10 damage, +1 attack speed, +100 movement speed и +48 range. Дублируйте подходящий ресурс из `res://content/demo/jobs/` и явно оставляйте ненужные прибавки равными нулю.

### Итоговый порядок расчёта

Герой:

1. `HeroDefinition.base_stats`.
2. Независимый рост каждой характеристики за уровень из `progression/demo_progression.tres`.
3. Модификаторы экипировки.

Солдат:

1. База ополченца.
2. `JobDefinition.stat_modifiers`.
3. Независимый рост каждой характеристики за veterancy.
4. Модификаторы экипировки.

Для предметов все операции `ADD` применяются раньше всех `MULTIPLY`, независимо от порядка в массиве.

## 4. Герои

Тип ресурса: `HeroDefinition`.

Примеры:

- `res://content/demo/heroes/Greed.tres`;
- `res://content/demo/heroes/Envy.tres`;
- `res://content/demo/heroes/Pride.tres`.

Поля героя:

| Поле | Назначение |
|---|---|
| `base_stats` | Полные базовые характеристики |
| `placeholder_color` | Цвет юнита на поле |
| `portrait` | Необязательная текстура портрета для карточки выбора; при отсутствии используется цветной placeholder с инициалами |
| `available_in_new_game` | Включает героя в carousel перед созданием нового забега |
| `selection_order` | Авторский порядок карточки в carousel |
| `tags` | В том числе определяет дальний тип героя |

Чтобы добавить героя:

1. Дублируйте ближайший по роли ресурс героя.
2. Назначьте новый уникальный `hero.*` ID.
3. Настройте полный `base_stats`.
4. Добавьте точный тег `ranged`, если герой должен использовать дальний тип базовой атаки.
5. Включите `available_in_new_game`, если герой должен участвовать в стартовом выборе.
6. Задайте уникальный `selection_order` и при наличии назначьте `portrait`.

`NEW GAME` открывает data-driven carousel всех зарегистрированных героев с `available_in_new_game = true`. Игрок выбирает ровно трёх; порядок нажатий `SELECT` становится порядком HeroState в roster и сохраняется в первом autosave. `DemoRunFactory.HERO_IDS` остаётся только default-составом для автономных тестов и технических preview, а не определяет реальный выбор игрока.

Текущий demo pool содержит семь героев. Четыре дополнительных героя не имеют собственных новых способностей. Чтобы геймдизайнер подключил будущую способность к одному или нескольким из них, достаточно добавить их `hero.*` IDs в `AbilityDefinition.allowed_hero_ids`, включить `available_to_heroes` и заполнить четыре `hero_levels`.

Новый герой начинает забег без способностей. После каждого обычного боя при входе в Management игрок выбирает одну из трёх случайных карточек Hero ability. Каждая карточка заранее назначена конкретному неказнённому герою. Новая способность сразу занимает свободный слот, а повтор уже известной способности повышает её уровень.

Ограничения runtime:

- у героя максимум 4 экипированные способности;
- у героя максимум 6 предметов;
- порядок применения активных способностей задаётся runtime-приоритетом игрока, а не полем `AbilityDefinition.priority`.

### Уровни героев

Параметры уровней находятся в `res://content/demo/progression/demo_progression.tres`:

| Поле | Что регулирует |
|---|---|
| `hero_level_xp_thresholds` | Суммарный Hero XP, необходимый для каждого уровня |
| `hero_max_hp_growth_per_level` | Процентный прирост max HP за уровень |
| `hero_damage_growth_per_level` | Процентный прирост damage за уровень |
| `hero_attack_speed_growth_per_level` | Процентный прирост attack speed за уровень |
| `hero_movement_speed_growth_per_level` | Процентный прирост movement speed за уровень |
| `hero_attack_range_growth_per_level` | Процентный прирост attack range за уровень |
| `hero_armor_growth_per_level` | Процентный прирост armor за уровень |

Hero Level начинается с `1`, поэтому Level 1 использует характеристики из `HeroDefinition.base_stats` без бонуса. Для каждой характеристики множитель рассчитывается независимо:

```text
gained_levels = max(Hero Level - 1, 0)
stat_multiplier = 1.0 + gained_levels * stat_growth_per_level
```

Текущие пороги равны `[0, 10, 25, 50, 250]`, а все шесть growth-полей равны `0.5`. Поэтому Level 2 получает +50%, Level 3 +100%, Level 4 +150%, Level 5 +200% к каждой характеристике. Growth применяется к базовым характеристикам героя до модификаторов предметов. Поля можно настраивать независимо, например оставить рост HP и armor высоким, не ускоряя одновременно damage и attack speed.

## 5. Солдаты и профессии

Отдельного `SoldierDefinition` нет. Каждый солдат является runtime-экземпляром, а его характеристики и способности определяются профессией `JobDefinition`.

Примеры:

- `res://content/demo/jobs/militia_job.tres`;
- `res://content/demo/jobs/warrior_job.tres`;
- `res://content/demo/jobs/archer_job.tres`;
- `res://content/demo/jobs/priest_job.tres`;
- `res://content/demo/jobs/summoner_job.tres`.

Поля профессии:

| Поле | Назначение |
|---|---|
| `stat_modifiers` | Прибавки к базе ополченца |
| `attack_type` | `melee` или `ranged` |
| `innate_ability_ids` | Врождённые способности каждого солдата профессии; не требуют покупки и не занимают слоты сборки |
| `available_ability_ids` | Способности, которые можно купить и поставить в сборку профессии |
| `capacity_price` | Цена ещё одного места профессии |
| `unlock_price` | Цена открытия профессии |
| `placeholder_color` | Цвет солдат этой профессии |

Чтобы добавить профессию:

1. Дублируйте наиболее похожую существующую профессию.
2. Назначьте новый `job.*` ID.
3. Настройте только прибавки `stat_modifiers`.
4. Выберите `attack_type`: `melee` или `ranged`.
5. При необходимости заполните `innate_ability_ids` и список покупаемых `available_ability_ids`.
6. Настройте `unlock_price` и `capacity_price`.
7. При необходимости добавьте предметы с ограничением на новый job ID.

Новая профессия автоматически становится кандидатом рынка на открытие. Исключение: точный ID `job.militia` никогда не предлагается рынком.

`job.summoner` использует `ability.summoner_job_summon` как врождённую active ability. Она всегда добавляется каждому Summoner и проверяется AI раньше покупаемых способностей. Её нельзя убрать или заменить через Job build.

Поля `attack_definition_id`, `ai_behavior` и `restriction_tags` сейчас преимущественно описательные. Новое значение в этих полях само по себе не создаёт новый тип атаки или AI.

Чтобы вручную изменить стартовых солдат, редактируйте `DemoRunFactory.create_starting_run()`:

- цикл `for index in 9` задаёт стартовое количество;
- `generated_name` задаёт имя;
- `current_job_id` можно назначить каждому создаваемому `SoldierState`;
- `run.unlocked_job_ids` задаёт открытые профессии;
- `run.job_capacities` задаёт стартовую вместимость профессий;
- `_job_build(...)` задаёт стартовые active/passive способности профессии.

### Veterancy солдат

Все доступные геймдизайнеру параметры veterancy находятся в `res://content/demo/progression/demo_progression.tres`:

| Поле | Что регулирует |
|---|---|
| `veterancy_xp_thresholds` | Суммарный XP, необходимый для каждого Veterancy Level |
| `veterancy_max_hp_growth_per_level` | Процентный прирост max HP за каждый уровень veterancy |
| `veterancy_damage_growth_per_level` | Процентный прирост damage за каждый уровень veterancy |
| `veterancy_attack_speed_growth_per_level` | Процентный прирост attack speed за каждый уровень veterancy |
| `veterancy_movement_speed_growth_per_level` | Процентный прирост movement speed за каждый уровень veterancy |
| `veterancy_attack_range_growth_per_level` | Процентный прирост attack range за каждый уровень veterancy |
| `veterancy_armor_growth_per_level` | Процентный прирост armor за каждый уровень veterancy |
| `damage_xp_rate` | XP за единицу нанесённого damage |
| `healing_xp_rate` | XP за единицу effective healing |
| `tanking_xp_rate` | XP за единицу damage tanked |
| `xp_rounding_mode` | Округление каждой категории: `FLOOR`, `ROUND` или `CEIL` |
| `max_contribution_xp` | Максимум XP за бой; `0` отключает ограничение |

#### Сколько XP получает солдат за бой

Фиксированного XP за участие, победу или выживание нет. Награда зависит от личного вклада:

```text
damage_xp  = round_mode(damage_dealt      * damage_xp_rate)
healing_xp = round_mode(effective_healing * healing_xp_rate)
tanking_xp = round_mode(damage_tanked     * tanking_xp_rate)

battle_xp = damage_xp + healing_xp + tanking_xp
```

Округление применяется к каждой категории отдельно, а не к итоговой сумме. При текущих коэффициентах `0.2` и режиме `FLOOR`:

| Вклад за бой | Расчёт | Полученный XP |
|---|---|---:|
| 120 damage | `floor(120 * 0.2)` | 24 |
| 80 tanking | `floor(80 * 0.2)` | 16 |
| 120 damage + 40 healing + 80 tanking | `24 + 8 + 16` | 48 |
| 9 damage + 9 healing + 9 tanking | `1 + 1 + 1` | 3 |

`effective_healing` не включает лишнее лечение поверх максимального HP. `max_contribution_xp` применяется после сложения трёх категорий.

XP начисляется и уровень пересчитывается после завершения боя. Только выживший Soldier сохраняет XP. Для погибшего Post Battle показывает `potential_xp`, но сам солдат удаляется; его replacement начинает с `0 XP`, Veterancy Level `0`, профессии Militia и пустой экипировки. Смена профессии также полностью сбрасывает накопленный XP и уровень. На поражении выжившие успевают получить XP, но текущий run после этого завершается.

Коэффициенты contribution сейчас общие для Hero XP и Soldier Veterancy XP. Изменение `damage_xp_rate`, `healing_xp_rate`, `tanking_xp_rate`, округления или cap одновременно влияет на обе системы. Если героям и солдатам нужны разные коэффициенты, это уже изменение кода, а не только ресурса.

#### Сколько XP нужно для следующего уровня

Текущий массив: `[0, 10, 25, 50, 100]`. Это накопительные пороги, а не стоимость отдельного уровня:

| Veterancy Level | Суммарный XP | XP от предыдущего уровня | До следующего уровня |
|---:|---:|---:|---:|
| 0 | 0-9 | старт | 10 |
| 1 | 10-24 | 10 | 15 |
| 2 | 25-49 | 15 | 25 |
| 3 | 50-99 | 25 | 50 |
| 4 | 100+ | 50 | максимальный уровень |

Первое значение массива должно оставаться `0`, остальные значения должны строго возрастать. Максимальный Veterancy Level равен `количество порогов - 1`. XP после последнего порога продолжает накапливаться, но новых уровней не даёт.

Чтобы изменить только скорость получения уровней, редактируйте пороги, а не contribution rates. Например, уменьшение порога Level 2 с `25` до `20` ускорит его получение, не меняя сравнительную награду damage, healing и tanking.

#### Какие бонусы даёт veterancy

Каждая характеристика имеет собственный growth за уровень. Итоговый множитель одной характеристики:

```text
stat_multiplier = 1.0 + Veterancy Level * stat_growth_per_level
```

Каждый множитель применяется независимо после сложения базы Militia и модификаторов профессии, но до предметов. Настраиваются:

- max HP;
- damage;
- attack speed;
- movement speed;
- attack range;
- armor.

Сейчас все шесть growth-полей равны `0.5`, поэтому текущие множители совпадают:

| Veterancy Level | Множитель | Бонус каждой характеристики |
|---:|---:|---:|
| 0 | `1.00` | 0% |
| 1 | `1.50` | +50% |
| 2 | `2.00` | +100% |
| 3 | `2.50` | +150% |
| 4 | `3.00` | +200% |

Пример для Warrior без предметов:

| Level | HP | Damage | Attack Speed | Movement | Range | Armor |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 185.00 | 12.00 | 1.00 | 108.00 | 46.00 | 14.00 |
| 1 | 277.50 | 18.00 | 1.50 | 162.00 | 69.00 | 21.00 |
| 2 | 370.00 | 24.00 | 2.00 | 216.00 | 92.00 | 28.00 |
| 3 | 462.50 | 30.00 | 2.50 | 270.00 | 115.00 | 35.00 |
| 4 | 555.00 | 36.00 | 3.00 | 324.00 | 138.00 | 42.00 |

Важно: одновременный рост нескольких характеристик сильнее одного бонуса того же размера. При текущем `+200%` к damage и attack speed сырой DPS Level 4 равен `3.0 * 3.0 = 9.0`, то есть растёт на 800%. HP и armor также усиливают выживаемость одновременно, а movement и range повышают фактическую эффективность позиционирования. Независимые поля позволяют ослабить такие сочетания без изменения остальных характеристик.

#### Как балансировать veterancy

1. Сначала определите желаемое число пережитых боёв до каждого уровня. Для короткого demo разумнее мыслить не абстрактным XP, а формулировкой вроде «средний выживший получает Level 1 после 2-3 боёв».
2. Соберите из Post Battle вклад солдат разных ролей: damage для Archer, tanking для Warrior, effective healing для Priest. Смотрите медиану, а не лучший результат одного юнита.
3. Если все роли растут слишком быстро или медленно, меняйте `veterancy_xp_thresholds`.
4. Если конкретная роль систематически отстаёт, сначала меняйте соответствующий XP rate. Помните, что это также изменит Hero XP.
5. Если один особенно успешный бой перескакивает несколько уровней, задайте `max_contribution_xp` или увеличьте расстояния между поздними порогами.
6. Если ветераны слишком сильны, уменьшайте growth-поля проблемных характеристик. Пороги регулируют скорость получения силы, а шесть growth-полей независимо регулируют её состав и размер.
7. Проверяйте стоимость адаптации: смена Job обнуляет veterancy. Игрок должен чувствовать потерю, но не отказываться от перестройки армии перед опасным Encounter.
8. Проверяйте permanent death отдельно. Высокий growth делает гибель ветерана очень болезненной и усиливает snowball между удачным и неудачным run.

Для каждой итерации фиксируйте хотя бы четыре значения: средний XP за бой по каждой профессии, бой получения каждого уровня, долю ветеранов, доживающих до Boss, и разницу времени победы между Level 0 и максимальным уровнем. После изменения прогрессии запускайте `tests/test_combat_results.gd`, `tests/test_stage6_builds.gd` и реальный полный маршрут.

## 6. Враги и боссы

### Обычный враг

Тип ресурса: `EnemyDefinition`.

Примеры:

- `res://content/demo/enemies/raider.tres`;
- `res://content/demo/enemies/crossbowman.tres`;
- `res://content/demo/enemies/summoner.tres`.

Поля:

| Поле | Назначение |
|---|---|
| `base_stats` | Полные базовые характеристики |
| `attack_type` | `melee` или `ranged` |
| `ability_ids` | Способности в порядке проверки AI |
| `placeholder_color` | Цвет врага |

Чтобы добавить врага:

1. Дублируйте существующего врага.
2. Назначьте новый `enemy.*` ID.
3. Настройте полный `base_stats`.
4. Выберите `attack_type`.
5. Добавьте существующие способности в `ability_ids`.
6. Добавьте ID врага в `enemy_ids` хотя бы одного encounter.

Новый враг автоматически зарегистрируется, но не появится в забеге без ссылки из столкновения.

### Босс

Тип ресурса: `BossDefinition`, наследует все поля врага.

Пример: `res://content/demo/enemies/iron_warden.tres`.

Дополнительные поля:

| Поле | Назначение |
|---|---|
| `phase_count` | Количество фаз |
| `phase_health_thresholds` | Доли HP для перехода на следующие фазы |
| `phase_damage_multiplier` | Множитель damage на каждой новой фазе |
| `phase_attack_speed_multiplier` | Множитель attack speed на каждой новой фазе |
| `telegraph_color` | Цвет предупреждения |
| `phase_telegraph_text` | Текст предупреждения |

Для `N` фаз нужно ровно `N - 1` порогов. Пороги задаются от большего к меньшему и находятся строго между 0 и 1. Например, три фазы могут иметь `[0.66, 0.33]`. Фазовые множители не могут быть меньше `1.0`.

## 7. Столкновения

Тип ресурса: `EncounterDefinition`.

Ресурсы разложены по актам: `res://content/demo/encounters/act_1/`, `act_2/` и пока пустой `act_3/`.

Длина маршрута настраивается отдельно в `res://content/demo/routes/demo_route.tres`:

| Поле | Назначение |
|---|---|
| `act_one_boss_wave` | Номер боя Act I с боссом; начинается с `1` |
| `act_two_battle_count` | Общее количество боёв Act II |

Сейчас `act_one_boss_wave = 12` и `act_two_battle_count = 12`, поэтому маршрут содержит двенадцать боёв Act I и двенадцать боёв Act II. Изменение `act_one_boss_wave` одновременно меняет длину Act I: победа над боссом переводит run в Execution, после которого начинается Act II.

| Поле | Назначение |
|---|---|
| `enemy_ids` | Точный состав врагов |
| `gold_reward` | Награда за победу |
| `act` | Акт 1 или 2 |
| `min_encounter_index` | Первый индекс боя, где карта доступна |
| `max_encounter_index` | Последний индекс боя, где карта доступна |
| `difficulty_hint` | `Low`, `Moderate`, `High` или `Boss` |
| `key_properties` | Свойства состава, видимые игроку |
| `is_unknown` | Скрывает состав карты |
| `is_boss` | Помечает боссовую карту |

Повтор одного ID в `enemy_ids` создаёт несколько экземпляров врага. Например, три одинаковых ID создадут трёх одинаковых врагов.

### Столкновения с подкреплением

Подкрепления настраиваются прямо в любом `EncounterDefinition`, включая boss-карты. Рабочие примеры находятся в `res://content/demo/encounters/act_1/reinforced_assault.tres` и `ogre_summon.tres`.

| Поле | Назначение |
|---|---|
| `enemy_ids` | Враги, которые находятся на поле в начале боя |
| `reinforcement_enemy_ids` | Враги, появляющиеся как подкрепление |
| `reinforcement_alive_threshold` | Подкрепление приходит, когда живых врагов остаётся не больше указанного числа; допустимы `0`, `1`, `2` |
| `reinforcement_entry_direction` | `ALL_SIDES` распределяет новых врагов по четырём краям арены, `RIGHT_SIDE` размещает всю группу у правого края |

Подкрепление приходит только один раз. Порог `0` означает, что сначала должна погибнуть вся стартовая группа, но бой не завершится: новые враги появятся до проверки победы. Для порогов `1` и `2` подкрепление вступает в бой одновременно с оставшимися врагами. Когда подкрепления включены, стартовая группа должна содержать больше врагов, чем указанный порог.

Чтобы включить механику у существующей обычной или boss-карты, заполните `reinforcement_enemy_ids`. Пустой массив полностью отключает подкрепления; значения порога и направления в этом случае не используются. Создавать другой тип ресурса или менять код не нужно.

У стартовых врагов runtime ID имеют вид `enemy-00`, а у подкрепления `enemy-reinforcement-00`, поэтому обе группы отдельно отображаются в боевой статистике. Карта Encounter показывает стартовый состав, состав подкрепления, порог и направление входа. Для unknown-карты оба состава скрываются.

В `EncounterDefinition` индексы начинаются с нуля, хотя `act_one_boss_wave` использует понятный дизайнеру номер с единицы:

| Часть маршрута | Индексы |
|---|---|
| Act I | `0..act_one_boss_wave - 1` |
| Boss Act I | `act_one_boss_wave - 1` |
| Act II | `0..act_two_battle_count - 1` |

Например, `act_one_boss_wave = 7` создаёт шесть обычных боёв с индексами `0..5` и Boss с индексом `6`. Boss-карты автоматически появляются только на настроенной boss-волне: их собственные `min_encounter_index` и `max_encounter_index` не управляют положением босса. Для каждого добавленного обычного индекса всё равно нужно расширить диапазоны существующих encounter-карт или создать минимум две новые известные карты.

Ограничения маршрута:

- на каждом слое требуется минимум две известные карты;
- на одном слое допускается максимум одна unknown-карта;
- unknown-карта должна давать больше золота, чем любая известная карта слоя;
- настроенная boss-волна Act I содержит только boss-карты;
- boss-карты запрещены на остальных слоях;
- известная карта должна иметь хотя бы одно `key_properties`;
- boss-карта должна иметь `difficulty_hint = "Boss"`;
- unknown-карта не может быть boss-картой.

Первый бой нового run является фиксированным tutorial: `encounter.training_skirmish` выбирается автоматически, после чего сразу открывается Management. Поэтому `act_one_boss_wave` должен быть не меньше `2`. После каждого обычного боя отдельный экран сначала предлагает ровно две карты следующего Encounter; выбранная карта открывает Management с выбором Hero ability. После Boss сначала выполняется обязательный Execution, затем выбирается первый Encounter Act II, после чего в Management показывается награда способности только для двух оставшихся героев.

В Management выбор Encounter не дублируется: выбранный бой кратко показан в header. Экран всегда состоит из армии по профессиям слева, контекстного инспектора по центру и Market с inventory справа. Soldier можно перетащить на заголовок профессии, Market Job ability на конкретный слот общей Job-сборки, а inventory или Market item на equipment slot. Hero abilities в Market не появляются. Job unlock и capacity по двойному клику применяются без экипировки. Двойной клик по предмету общего Inventory автоматически занимает первый свободный слот выбранного Hero/Soldier, а при полном наборе заменяет выбранный equipment slot. Чтобы снять предмет, перетащите занятый equipment slot на заголовок общего Inventory.

## 8. Способности

Тип ресурса: `AbilityDefinition`.

Примеры находятся в `res://content/demo/abilities/`.

### Основные поля

| Поле | Назначение |
|---|---|
| `kind` | `ACTIVE` или `PASSIVE` |
| `cooldown_seconds` | Перезарядка активной способности |
| `targeting_policy` | Правило выбора цели |
| `excluded_target_status_id` | Status ID, который исключает цель для `RANDOM_ENEMY_WITHOUT_STATUS` |
| `delivery_method` | Способ доставки |
| `effects` | Эффекты в порядке исполнения |
| `area_radius` | Радиус AoE |
| `presentation_color` | Цвет снаряда или телеграфа |
| `presentation_text` | Текст телеграфа |
| `rarity` | Редкость; также задаёт вес способности профессии в Market |
| `price` | Цена способности профессии в Market; Hero reward бесплатна |
| `available_to_heroes` | Может ли способность участвовать в послебоевом выборе героев; выключите для служебных способностей Jobs и врагов |
| `allowed_hero_ids` | Герои, которым может быть назначена способность; пустой список означает всех героев |
| `hero_levels` | Ровно четыре полных набора параметров `AbilityLevelDefinition` для Hero-версии |

`priority` не определяет обычный игровой порядок героя. Для врага порядок задаёт `EnemyDefinition.ability_ids`, а для героя порядок хранится в его runtime-сборке.

### Выбор цели

| Значение | Поведение |
|---|---|
| `SELF` | Сам владелец |
| `CLOSEST_ENEMY` | Ближайший враг |
| `LOWEST_HP_ALLY` | Повреждённый союзник с наименьшей долей HP |
| `RANDOM_VALID_ENEMY` | Случайный живой враг |
| `NEAREST_NEGATIVE_STATUS_ALLY` | Ближайший союзник хотя бы с одним негативным статусом |
| `RANDOM_ENEMY_WITHOUT_STATUS` | Случайный живой враг без `excluded_target_status_id` |

`LOWEST_HP_ALLY` не активируется, если все союзники имеют полное здоровье. `RANDOM_ENEMY_WITHOUT_STATUS` не активируется, если указанный статус уже есть на всех живых врагах.

### Доставка

| Значение | Поведение |
|---|---|
| `INSTANT` | Мгновенное применение |
| `MELEE_HIT` | Требует подойти к цели |
| `PROJECTILE` | Создаёт снаряд |
| `AREA_AROUND_TARGET` | Применяет эффекты ко всем подходящим юнитам в радиусе цели |

Для AoE обязательно задайте `area_radius > 0`. Комбинация `SELF + AREA_AROUND_TARGET` создаёт область вокруг владельца и подходит для массового усиления союзников.

### Доступные эффекты

| Тип | Поля | Назначение |
|---|---|---|
| `DamageEffect` | `amount` | Фиксированный сырой урон |
| `HealEffect` | `amount` | Фиксированное лечение |
| `ShieldEffect` | `amount`, `duration` | Временный щит |
| `ApplyStatusEffect` | `status` | Наложение StatusDefinition |
| `StatModifierEffect` | `modifier`, `duration` | Временное изменение характеристики |
| `SummonEffect` | `summoned_unit`, `max_active_summons`, `summoner_contribution_percent` | Призывает рядом с владельцем одного временного юнита и передаёт владельцу настроенную долю contribution |
| `BasicAttackEmpowerEffect` | `lifesteal_percent`, `size_multiplier`, `duration` | Временно даёт вампиризм только базовым атакам и масштабирует модель вместе с collision radius |

Каждому эффекту задавайте понятный `effect_id`, например `effect.ice_nova_damage`. Этот ID используется в событиях и статистике, но его уникальность автоматически не проверяется.

Эффекты выполняются по порядку массива. Если цель погибла от первого эффекта, следующие эффекты на неё не применятся. Например, если сначала стоит смертельный damage, следующий burn может не наложиться.

Пассивная способность применяет свои эффекты один раз к владельцу при создании юнита. Её cooldown не используется.

### Уровни Hero abilities

Каждая способность с `available_to_heroes = true` обязана содержать ровно четыре элемента `hero_levels`. Каждый `AbilityLevelDefinition` независимо задаёт:

| Поле | Назначение |
|---|---|
| `cooldown_seconds` | Cooldown этого уровня |
| `area_radius` | AoE radius этого уровня |
| `effects` | Полный список эффектов этого уровня с конкретными amount, duration, status или summon-параметрами |

Level 1 должен воспроизводить базовую Hero-версию способности. Верхнеуровневые `cooldown_seconds`, `area_radius` и `effects` сохраняются для Job и Enemy, если та же способность назначена им отдельно. Combat snapshot героя использует набор из `hero_levels` согласно сохранённому уровню способности.

После боя генератор сначала старается показать три разные способности. Каждая карточка содержит пару Hero + Ability. Один герой может получить несколько карточек, но выбрать можно только одну. Если разных допустимых способностей меньше трёх, разрешаются повторяющиеся карточки. Новые способности имеют вес `RouteDefinition.new_hero_ability_weight`, повышения уровня — `RouteDefinition.hero_ability_upgrade_weight`. По умолчанию это `3` и `1`.

Новая способность не предлагается герою с четырьмя занятыми слотами. Уже известная способность может предлагаться при полных слотах и повышается на один уровень. Level 4 является максимальным и больше не попадает в пул. Если допустимых вариантов нет вообще, окно награды пропускается.

### Призыв существ

Для призыва используйте active ability с `SELF`, `INSTANT` и одним `SummonEffect`. Настройка распределена так:

| Поле | Что регулирует |
|---|---|
| `SummonEffect.summoned_unit` | Какой `EnemyDefinition` используется как шаблон призыва |
| `SummonEffect.max_active_summons` | Сколько живых существ этого эффекта одновременно может иметь один кастер |
| `SummonEffect.summoner_contribution_percent` | Какой процент от damage, healing и tanking призыва получает владелец для расчёта XP; допустимо `0..100` |
| `AbilityDefinition.cooldown_seconds` | Как часто кастер пытается призвать следующего юнита |

Каждое применение создаёт ровно одного юнита рядом с кастером. Готовая summon-способность имеет высший приоритет: после завершения cooldown она прерывает движение, обычный attack windup и attack recovery/отступление. Stun по-прежнему запрещает её применение. При заполненном лимите способность не применяется, не запускает cooldown и не прерывает текущее действие. Погибший призыв сразу освобождает место.

Призывы наследуют команду и Veterancy Level кастера. Унаследованный уровень применяет к их собственным базовым характеристикам все шесть настроек `veterancy_*_growth_per_level`. Настроенная через `summoner_contribution_percent` доля damage dealt, effective healing и damage tanked призыва записывается его владельцу и aggregate владельца, поэтому Soldier Summoner получает соответствующую долю veterancy XP и lifetime statistics. При `0` призывы не дают владельцу contribution, при `100` передают её полностью. Оставшаяся доля отбрасывается и не даёт XP самому временному существу. Его damage taken и death остаются видны для диагностики боя. Призывы исчезают после боя, сами не получают progression, не занимают места армии и не считаются permanent death.

Шаблоны слабых призывов находятся в `res://content/demo/enemies/summoned_brawler.tres` и `summoned_shooter.tres`. Конфигурации врага, Job и героя независимы:

| Получатель | Ability |
|---|---|
| Enemy Summoner | `ability.enemy_summon` |
| Summoner Job | `ability.summoner_job_summon` через `innate_ability_ids` |
| Герои | `ability.hero_summon`, обычная послебоевая способность |

### Как добавить способность

1. Дублируйте ближайшую способность, например `fire_bolt.tres` или `guardian_shield.tres`.
2. Назначьте новый `ability.*` ID.
3. Выберите `ACTIVE` или `PASSIVE`.
4. Выберите совместимые target и delivery.
5. Создайте или замените вложенные эффекты.
6. Проверьте порядок эффектов.
7. Настройте cooldown, rarity и price для базовой Job/Enemy-версии.
8. Для Hero-compatible способности создайте ровно четыре полных `hero_levels`.
9. Подключите способность герою, профессии или врагу по ID.

Способы подключения:

| Получатель | Поле |
|---|---|
| Герой | Послебоевая карточка автоматически назначается конкретному совместимому Hero |
| Профессия | `JobDefinition.available_ability_ids` |
| Врождённая способность профессии | `JobDefinition.innate_ability_ids` |
| Враг или босс | `EnemyDefinition.ability_ids` |
| Любой герой через reward | Автоматически для AbilityDefinition с включённым `available_to_heroes` |

Новая способность становится кандидатом послебоевой награды только при включённом `available_to_heroes`. Карточки могут назначаться живым и мёртвым героям, но никогда казнённым. Пустой `allowed_hero_ids` делает способность универсальной для всех героев. Ограничение героев не мешает отдельно назначать ту же способность профессиям и врагам.

При покупке Job ability должен быть выбран Soldier нужной профессии или заголовок самой профессии. Active ability заменяет текущий active slot. Passive ability занимает первый свободный passive slot; если все три заняты, предложение нужно перетащить на конкретный заменяемый слот.

Текущее распределение demo-способностей:

| Способность | Герои |
|---|---|
| `ability.whirlwind` | Greed |
| `ability.mending_light` | Envy |
| `ability.fortify` | Envy |
| `ability.frost_dart` | Недоступна героям |
| `ability.stunning_blow` | Greed |
| `ability.fire_bolt` | Greed |
| `ability.guardian_shield` | Envy |
| `ability.battle_fury` | Все герои, кроме Pride; явный список |
| `ability.hero_summon` | Все герои, кроме Pride; явный список |
| `ability.pride_last_stand` | Pride |
| `ability.pride_farthest_attack` | Pride |
| `ability.pride_cleanse` | Pride |
| `ability.pride_sacrifice` | Pride |

| `ability.pride_attack_speed_aura` | Pride |

При наведении на способность интерфейс показывает описание, тип, выбор цели, способ доставки, cooldown, AoE, допустимых героев и полную цепочку эффектов. Для накладываемого статуса также показываются длительность, стаки, периодические эффекты и модификаторы.

## 9. Статусы

Тип ресурса: `StatusDefinition`.

Примеры находятся в `res://content/demo/statuses/`.

| Поле | Назначение |
|---|---|
| `default_duration` | Длительность статуса |
| `max_stacks` | Максимум стаков |
| `stack_policy` | Обновить длительность или добавить стак |
| `periodic_interval` | Интервал периодических эффектов |
| `periodic_effects` | Эффекты каждого тика |
| `stat_modifiers` | Модификаторы на время статуса |
| `prevents_actions` | Полностью запрещает действия |
| `polarity` | `POSITIVE`, `NEGATIVE` или `NEUTRAL`; cleanse снимает только `NEGATIVE` |

`REFRESH_DURATION` обновляет длительность без добавления стака. `ADD_STACKS` обновляет длительность и увеличивает число стаков до `max_stacks`.

Для периодического статуса задайте и `periodic_interval`, и `periodic_effects`. Каждый periodic-эффект выполняется отдельно за каждый стак.

`default_duration = 0` создаёт статус до конца боя. Положительное значение задаёт длительность в секундах. Для `ShieldEffect` и `StatModifierEffect` duration `0` также означает бессрочный эффект.

Чтобы использовать статус в способности, добавьте `ApplyStatusEffect` и назначьте в его поле `status` прямую ссылку на `.tres` статуса.

## 10. Предметы

Тип ресурса: `ItemDefinition`.

Примеры находятся в `res://content/demo/items/`.

| Поле | Назначение |
|---|---|
| `allowed_target_type` | Только `hero` или `soldier` |
| `allowed_job_ids` | Разрешённые профессии солдат |
| `passive_effects` | Постоянные `StatModifier` |
| `rarity` | Редкость и вес на рынке |
| `price` | Цена покупки |
| `sell_price` | Цена продажи; `0` запрещает продажу |

`StatModifier` содержит:

| Поле | Значение |
|---|---|
| `stat` | `max_hp`, `damage`, `attack_speed`, `movement_speed`, `attack_range` или `armor` |
| `operation = ADD` | Прибавить `value` |
| `operation = MULTIPLY` | Умножить на `value` |
| `value` | Число прибавки или множитель |

Для +20% HP используйте `stat = max_hp`, `operation = MULTIPLY`, `value = 1.2`. Значение `0.2` уменьшит HP до 20%, а не добавит 20%.

Чтобы добавить предмет:

1. Дублируйте ближайший предмет.
2. Назначьте новый уникальный ID.
3. Выберите `hero` или `soldier`.
4. Для hero-предмета оставьте `allowed_job_ids` пустым.
5. Для soldier-предмета оставьте список пустым для всех профессий или перечислите допустимые job ID.
6. Настройте `passive_effects`.
7. Задайте rarity, price и sell_price.

Новый предмет автоматически становится кандидатом рынка. Soldier-предмет с ограничениями появится только тогда, когда открыта хотя бы одна разрешённая профессия.

В инвентаре хранятся экземпляры, а не только типы предметов. Два одинаковых предмета имеют один `definition_id`, но разные `instance_id`, поэтому их эффекты могут складываться.

Ограничения экипировки:

- герой может носить до 6 предметов;
- солдат может носить до 2 предметов;
- один экземпляр нельзя экипировать дважды;
- экипированный предмет нельзя продать;
- предмет с ограничением профессии блокирует смену профессии, пока предмет не снят.

Предметы в общем Inventory не выделяются. У каждого доступного экземпляра есть собственная кнопка продажи. Двойной клик сразу экипирует предмет выбранному Hero/Soldier, а перенос занятого equipment slot на заголовок Inventory возвращает экземпляр в общий список.

Чтобы выдать стартовый предмет вручную, добавьте его ID в массив в `DemoRunFactory.create_starting_run()`, где вызывается `run.inventory.create_item(item_id)`.

В текущем prototype зарегистрированы только два предмета, и оба предназначены для героев: `item.hero.vanguard_blade` и `item.hero.titan_seal`.

## 11. Рынок

Рынок не хранится в отдельном `.tres` и не имеет ручного списка предложений. Предложения генерируются автоматически из предметов, профессий и способностей профессий с учётом текущего состояния забега. Hero abilities в Market не участвуют.

Возможные предложения:

| Тип | Источник |
|---|---|
| Предмет героя | Любой `ItemDefinition` с target `hero` |
| Открытие профессии | Любой закрытый `JobDefinition`, кроме `job.militia` |
| Вместимость профессии | Открытая профессия, если вместимость меньше числа солдат |
| Способность профессии | `JobDefinition.available_ability_ids` |
| Предмет солдата | `ItemDefinition` с target `soldier` и подходящими job-ограничениями |

### Что настраивается данными

| Желаемое изменение | Где менять |
|---|---|
| Цена способности | `AbilityDefinition.price` |
| Редкость способности | `AbilityDefinition.rarity` |
| Цена предмета | `ItemDefinition.price` |
| Цена продажи | `ItemDefinition.sell_price` |
| Редкость предмета | `ItemDefinition.rarity` |
| Цена открытия профессии | `JobDefinition.unlock_price` |
| Цена вместимости | `JobDefinition.capacity_price` |
| Набор способностей профессии | `JobDefinition.available_ability_ids` |

Редкость влияет на вероятность выбора кандидата:

| Редкость | Базовый вес |
|---|---:|
| `common` | 100 |
| `uncommon` | 55 |
| `rare` | 25 |
| `legendary` | 8 |

За один визит рынок создаёт 5-7 предложений. Если доступны обе группы, генератор сначала старается выбрать хотя бы одно предложение для героев и одно для армии. Генерация требует минимум пяти подходящих кандидатов.

Рынок мягко повышает вероятность дорогих предложений для менее развитых героев. Это не гарантия конкретного предмета или способности.

### Что требует изменения кода

| Настройка | Файл и константа |
|---|---|
| Минимум предложений | `market_generator.gd`, `MIN_OFFERS` |
| Максимум предложений | `market_generator.gd`, `MAX_OFFERS` |
| Веса редкости | `market_generator.gd`, `RARITY_WEIGHTS` |
| Начальная цена reroll | `market_service.gd`, `BASE_REROLL_PRICE` |
| Рост цены reroll | `market_service.gd`, `REROLL_PRICE_STEP` |

Не добавляйте постоянное предложение напрямую в `MarketState.offers`: это runtime-состояние, оно пересоздаётся при новом визите или reroll и сериализуется в сохранение. Для постоянного присутствия нужен отдельный механизм генерации или гарантированного выбора в `MarketGenerator`.

## 12. Частые ошибки

| Ошибка | Последствие | Решение |
|---|---|---|
| Повторяющийся `id` | Registry отклоняет ресурс | Использовать глобально уникальный ID |
| Переименование старого ID | Ломаются ссылки и сохранения | Не менять ID выпущенного контента |
| Новый герой не появляется | Герой не добавлен в стартовый список | Обновить `DemoRunFactory.HERO_IDS` |
| Новый враг не появляется | Нет ссылки из encounter | Добавить ID в `enemy_ids` |
| Профессия слишком сильная | Использованы defaults нового StatBlock | Дублировать job и обнулить ненужные прибавки |
| Герой с большой range идёт в melee | Нет тега `ranged` | Добавить точный тег `ranged` |
| Способность бесплатна | Не заполнен `price` | Задать цену до проверки рынка |
| AoE не задевает соседей | `area_radius = 0` | Задать ненулевой радиус |
| Лечение применяется не туда | Неверный targeting policy | Использовать `LOWEST_HP_ALLY` или `SELF` |
| Эффект после damage не сработал | Цель умерла от предыдущего эффекта | Изменить порядок эффектов |
| Статус сразу исчезает | `default_duration = 0` | Задать положительную длительность |
| Множитель +20% уменьшает stat | Указано `0.2` вместо `1.2` | Для +20% использовать `1.2` |
| Предмет солдата не появляется | Его job ещё закрыт | Открыть разрешённый job или убрать ограничение |
| Registry прошёл, но ability не работает | Не все ID-ссылки валидируются автоматически | Запустить профильные тесты и реальный бой |

## 13. Проверка изменений

После изменения контента сначала запустите проект из редактора. Ошибки Registry появятся в панели Output.

Для автоматической проверки из корня проекта используйте Godot в headless-режиме:

```powershell
godot --headless --path . --script tests/test_data_layer.gd
godot --headless --path . --script tests/test_abilities.gd
godot --headless --path . --script tests/test_combat.gd
godot --headless --path . --script tests/test_stage9_items.gd
godot --headless --path . --script tests/test_stage11_market.gd
godot --headless --path . --script tests/test_stage12_encounters.gd
godot --headless --path . --script tests/test_stage14_execution.gd
```

Запускайте команды последовательно. Для этого проекта несколько одновременно запущенных экземпляров Godot могут конфликтовать при обновлении `.godot/global_script_class_cache.cfg`.

Минимальный набор по типу изменения:

| Изменение | Проверки |
|---|---|
| Герой, профессия или враг | `test_data_layer`, `test_combat` |
| Способность или статус | `test_abilities`, `test_combat` |
| Предмет | `test_stage9_items`, `test_stage11_market` |
| Рынок | `test_stage11_market` |
| Encounter | `test_stage12_encounters` |
| Босс | `test_stage14_execution` |

Автотесты не заменяют визуальную проверку. После успешных тестов проведите хотя бы один бой с новым контентом и проверьте числа в realtime-панели статистики и карточке выбранного юнита.

## 14. Граница между контентом и программированием

Можно сделать только ресурсами:

- изменить числовые характеристики;
- создать героя, профессию, врага или босса из существующих механик;
- собрать способность из существующих эффектов;
- создать предмет с существующими модификаторами;
- изменить состав, награду и доступность encounter;
- изменить цены и редкость рыночного контента.

Потребуется программирование:

- новая характеристика;
- новый алгоритм выбора цели;
- новый тип эффекта способности;
- масштабирование эффекта от damage или HP;
- новый AI behavior;
- новая логика базовой атаки;
- гарантированные или закреплённые предложения рынка;
- новый тип валюты или правила магазина.

Если требуемое поведение отсутствует в доступных enum или типах эффектов, произвольная новая строка в `.tres` его не создаст.

## 15. События между боями

Тип ресурса: `RunEventDefinition`. Событие случайно определяется после завершения боя и открывается поверх Management после выбора следующего Encounter. Выбранное событие, текущий узел ветки и случайные Soldier targets сохраняются сразу, поэтому загрузка не меняет результат броска. Каждый подтверждённый вариант также сохраняется отдельно.

Пример: `res://content/demo/events/old_shrine.tres`.

### Частота

| Поле | Назначение |
|---|---|
| `RunEventDefinition.weight` | Относительный вес события среди подходящих событий |
| `RunEventDefinition.one_time` | Запрет повторного появления в текущем забеге; по умолчанию включён |
| `RouteDefinition.event_absence_percent` | Независимая вероятность отсутствия события от `0` до `100` процентов |

Сначала отдельно проверяется `event_absence_percent`. Если событие должно произойти, конкретное событие выбирается пропорционально `weight` среди подходящих кандидатов. Условия с false, события с нулевым весом и уже выпавшие одноразовые события в выбор не входят.

### Случайные Soldier targets

| Поле | Назначение |
|---|---|
| `soldier_target_count` | Количество разных случайных Soldier, фиксируемых для события |
| `target_allowed_job_ids` | Допустимые Jobs; пустой список разрешает любые |
| `target_min_veterancy_level` | Минимальный Veterancy Level кандидата |

Targets выбираются без повторений через persisted Event RNG. В тексте узла и варианта используйте `{soldier_0}`, `{soldier_1}` и далее. При показе они заменяются сохранёнными именами выбранных солдат. Если подходящих Soldier меньше, чем `soldier_target_count`, событие не участвует в выборе.

### Ветки диалога

`RunEventDefinition.nodes` содержит плоский список `RunEventNode`, а `entry_node_id` задаёт начало. Каждый узел содержит title, body и массив `RunEventChoice`.

| Поле выбора | Назначение |
|---|---|
| `choice_id` | Уникальный ID внутри узла |
| `text` | Текст кнопки |
| `conditions` | Условия доступности |
| `effects` | Эффекты, применяемые одной атомарной транзакцией |
| `next_node_id` | Следующий узел; пустое значение завершает событие |

Если хотя бы один эффект применить нельзя, вариант блокируется целиком. Например, Hero ability нельзя выбрать при четырёх занятых слотах, active Job ability нельзя получить при занятом active slot, а passive Job ability блокируется при трёх занятых passive slots.

### Условия

`RunEventCondition.condition_type` поддерживает:

- `ALWAYS`;
- диапазон Act;
- минимальное Gold;
- наличие доступного Hero;
- открытый Job;
- минимальное число Soldier;
- наличие предмета;
- диапазон Veterancy у сохранённого Soldier target.

Поле `inverted` инвертирует результат. Event-level условия проверяются до случайного выбора события. Choice-level условия повторно проверяются при показе и подтверждении варианта.

### Эффекты

`RunEventEffect.effect_type` поддерживает:

- добавление предмета в общий Inventory без экипировки;
- выдачу и немедленную экипировку Hero ability;
- выдачу и немедленную установку общей Job ability;
- постоянный или временный stat modifier отдельному Hero, случайному Soldier либо всему Job;
- увеличение или уменьшение Hero Level;
- увеличение или уменьшение Veterancy случайных Soldier;
- увеличение или уменьшение Job capacity.

Для Level и Veterancy XP переводится на минимальный порог нового уровня. Значения ограничиваются существующим диапазоном уровней.

Для `STAT_MODIFIER` настройте:

| Поле | Назначение |
|---|---|
| `target_scope` | `HERO`, `SOLDIER_TARGET` или `JOB` |
| `hero_definition_id` / `job_id` | Фиксированная цель для Hero или Job |
| `target_index` | Индекс случайного Soldier target |
| `all_soldier_targets` | Применить ко всем выбранным Soldier |
| `stat` | Одна из шести боевых характеристик |
| `modifier_operation` | `ADD` или `MULTIPLY` |
| `modifier_value` | Положительный бонус либо отрицательный/уменьшающий штраф |
| `battles_remaining` | `-1` для постоянного эффекта или число будущих боёв |

Временный modifier с длительностью `1` действует в следующем бою и удаляется после применения его результата. Preview, restart боя и переходы между экранами длительность не расходуют.
